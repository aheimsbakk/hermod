The core design is strong. The code uses TLS 1.3, QUIC peer certificate pinning, CPace with `crypto/ecdh`, AES-256-GCM with channel-bound AAD, strict file-permission defaults, and layered path-traversal defenses. I did not find a direct payload-confidentiality break.

`CGO_ENABLED=1 go test -race ./...` did not change the security ranking. It surfaced concurrency problems in test harnesses and concurrent in-process CLI tests, but it did not expose a new cryptographic, transport, or server-side runtime data race.

## Findings

### ✅ High — Expired channels do not expire live waiters or WebSocket relays (Resolved)

**Files:** `internal/server/server.go`, `internal/server/store.go`

`server.RunGC()` only calls `store.PurgeExpired()`. `MemoryStore.PurgeExpired()` removes expired entries from the store, but it does not close the WebSocket connections or remove `Server.waiters[channelID]`. The relay goroutine keeps blocking on `conn.ReadJSON()` with no WebSocket read deadline or heartbeat.

**Resolution:**

- `PurgeExpired()` now returns expired channel IDs. The GC loop in `Serve()` passes them to `purgeExpiredWaiters()` which closes all waiter connections and removes them from the map.
- `handleAllocate()` cleans up stale waiters for the channel ID before adding a new sender.
- `handleWS()` sets a 2-minute `SetReadDeadline` and a `SetPongHandler` that extends the deadline on each pong, preventing idle connections from living indefinitely.

### ✅ Medium — Client accepts unbounded WebSocket messages from an untrusted relay (Resolved)

**Files:** `internal/network/signaling.go`

The client never calls `conn.SetReadLimit()` after opening the signaling WebSocket. The server enforces a 64 KiB read limit for inbound client messages, but the client does not enforce a matching limit for server messages.

Hermod's threat model treats the signaling server as untrusted. A malicious or compromised relay can send an oversized JSON message or blob and force `ReadJSON()` to allocate large amounts of memory on `tx` or `rx`.

**Resolution:**

- `dialSignaling()` now calls `conn.SetReadLimit(maxMessageSize)` (64 KiB) after the dial succeeds.
- `Recv()` rejects decoded messages whose `Payload` exceeds `maxMessageSize`.

### ✅ Medium — Receiver fails open when the trailing hash stream is missing or unreadable (Resolved)

**Files:** `internal/cli/rx.go`, `pkg/transfer/transfer.go`

After saving the payload, `rx` tries to read the trailing hash stream. If `AcceptStream()` fails, or if `readLenPrefixedMax()` fails, the code logs a warning and still reports success.

That makes the final integrity step optional in practice. A broken or malicious peer can skip the trailing hash, and a post-payload connection failure can still end with `Receive and verification complete.`

**Resolution:**

- `saveToFile()` no longer renames the temp file to its final destination. It returns the temp path, destination path, computed hash, and byte count.
- `runRx()` treats missing or unreadable trailing hash as a fatal error, removes the temp file, and returns an error.
- Received byte count is compared against `meta.Size` before verification.
- `HashStream()` now returns the number of bytes written alongside the hash digest.

### ✅ Low — Plaintext `ws://` mode is still allowed, and `trust` can pin a fingerprint that `tx`/`rx` will never use (Resolved)

**Files:** `internal/network/signaling.go`, `internal/cli/trust.go`

`tx` and `rx` still allow `ws://` signaling URLs. The runtime warning helps, but the mode remains available. `trust` can also store a fingerprint under a `ws://` URL even though the later signaling session is plaintext and does not use TLS pinning at all.

**Resolution:**

- `dialSignaling()` now returns an error for `ws://` instead of a warning.
- `runTrust()` rejects `ws://` URLs with an error before making any network call.

## Informational

### ℹ️ Info — `--max-cpace-failures` does not count wrong transfer-code guesses (Acknowledged)

**Files:** `internal/server/server.go`

The server increments the failure counter only on relay-side protocol violations or storage failures. It does not observe wrong-password CPace failures, because those happen end-to-end on the clients when endpoint-bundle decrypts fail.

This is not a direct exploit, but operators should not assume the flag limits incorrect transfer-code guesses per channel. The real online control is the join and WebSocket rate limit.

### ✅ Info — `SASFromBytes()` still contains a biased fallback path (Resolved)

**Files:** `internal/crypto/crypto.go`

The fallback branch uses `byte % n`, which is biased. On current call sites it is unreachable because SAS generation always receives 32 bytes from `ExportKeyingMaterial()`.

**Resolution:**

- Replaced the biased modulo fallback with a `panic`, since the path is unreachable — all callers provide at least 32 bytes of key material.

## Positive observations

- `tx` and `rx` require a pinned signaling-server certificate before normal use. `trust` is the only TOFU entry point.
- QUIC peers pin each other's ephemeral certificate fingerprints inside the encrypted endpoint bundle.
- CPace now uses `crypto/ecdh.P256()` instead of deprecated secret `ScalarMult()`.
- Long DST handling in hash-to-curve follows RFC 9380 oversize-DST encoding.
- Endpoint bundles bind the channel ID as AES-GCM AAD.
- Receiver temp files use `0o600` and `O_EXCL`.
- Filename handling applies `filepath.Base()` and safe destination selection.
- HTTP server timeouts, WebSocket handshake timeout, and `/cert` response size limits are in place.
- No hardcoded credentials or tokens were found in the reviewed source, scripts, or workflow files.
- I did not find any production use of `eval`, shelling out, or other dynamic code-execution patterns.

  - `internal error: package "golang.org/x/sys/unix" without types was imported from "github.com/mattn/go-isatty"`

## Limitations

- Some `-race` failures came from test scaffolding that runs multiple CLI invocations inside one process by sharing package globals and reassigning process-global stdio. That is a real test reliability issue, but it is not reachable in the normal one-command-per-process CLI deployment model.
- The automated dependency scan was incomplete because `govulncheck` failed before it could finish module analysis.

## Resolution

All findings were resolved on 2026-06-11. The recommended order was followed:

1. ✅ Live channel expiry and stale waiter cleanup — `purgeExpiredWaiters()`, WebSocket read deadlines + pong handler, stale waiter rejection in `handleAllocate()`.
2. ✅ Client-side WebSocket read limit — `conn.SetReadLimit(maxMessageSize)` in `dialSignaling()` plus post-decode payload size validation.
3. ✅ Trailing-hash verification fail-closed — delayed rename until after hash verification, byte-count check, fatal error on missing hash.
4. ✅ `ws://` rejected by default in both `dialSignaling()` and `runTrust()`.

All `go build ./...`, `go vet ./...`, and `go test ./...` pass.
