## What the Codebase Gets Right

Across all three audits, the following security controls and design decisions were
called out as well-implemented. This list is deduplicated — each item appears once.

| # | Control | Notes |
|---|---------|-------|
| 1 | **Zero-knowledge relay.** Signaling server never receives plaintext endpoint data or payload. CPace ensures the password never crosses the network. | All audits |
| 2 | **Ephemeral QUIC cert fingerprint pinning.** Cert fingerprints exchanged inside the AES-GCM endpoint bundle prevent MitM during the QUIC handshake. | Sonet46, deepseek-v4 |
| 3 | **TLS 1.3 enforcement + post-quantum KEM.** `MinVersion: tls.VersionTLS13` everywhere. Cipher/curve preferences prefer X25519MLKEM768 then X25519. | Sonet46, deepseek-v4 |
| 4 | **SHA-256 integrity stream with parallel hashing.** Hash computed during transfer, sent as trailing metadata stream after payload. Temp-file-then-rename pattern prevents partial files. | Sonet46, flash-max, deepseek-v4 |
| 5 | **Rate limiting with IP anonymization.** Token bucket per /32 IPv4, /64 IPv6. Bucket keys are HMAC-SHA256(daily-rotating salt, prefix). Raw IPs are never stored. | Sonet46, flash-max, deepseek-v4 |
| 6 | **CPace failure circuit-breaker.** Three failed CPace attempts drop the channel, blocking online brute-force. | Sonet46, deepseek-v4 |
| 7 | **SAS out-of-band verification.** Derived from TLS `ExportKeyingMaterial`, bound to the full TLS session. Identicon adds a visual comparison channel. Symmetric enforcement (either side can require it). | Sonet46, deepseek-v4 |
| 8 | **AES-256-GCM with AAD for endpoint bundles.** The channel ID (2-byte big-endian) is bound as Additional Authenticated Data to tie ciphertext to the session. | flash-max, deepseek-v4 |
| 9 | **Constant-time cert fingerprint comparison.** Uses `crypto/subtle.ConstantTimeCompare` instead of Go string equality. | deepseek-v4 |
| 10 | **TOCTOU prevention on duplicate receiver joins.** Mutex lock held across check-and-insert, preventing two receivers from joining the same channel. | deepseek-v4 |
| 11 | **Per-channel blob and CPace failure limits.** 10 blobs max per channel. Prevents resource exhaustion per session. | deepseek-v4 |
| 12 | **WebSocket Origin check.** Cross-origin connections from browsers are rejected. | deepseek-v4 |
| 13 | **Ephemeral P-256 certs for QUIC.** 2-hour validity (reduced from 24h in v0.16.1), regenerated per transfer. Fast generation and small wire footprint. | Sonet46, deepseek-v4 |
| 14 | **SAS prompt reads from `/dev/tty` (Unix) / `CONIN$` (Windows).** Won't capture piped stdin content if stdout is redirected. | deepseek-v4 |
| 15 | **Graceful cancellation.** QUIC `ApplicationError` with typed cancellation codes allows either peer to abort cleanly. | Sonet46 |

#### SUM-01: M-04 / #5 — Channel ID space exhaustion (DoS) — [OPEN]

**Source:** Sonet46 M-04, deepseek-v4 #5

**Description:** The channel ID is a `uint16`, giving 65,536 possible channels. A
distributed attacker with ~13,100 source IPs can allocate all channels in one second
(the rate limiter allows 5 alloc/s per IP). With a 10-minute TTL, the exhaustion
can be sustained indefinitely, preventing legitimate transfers.

**Current state:** Rate limiting partially mitigates (5 req/s per IP, 3 CPace failures
drops the channel), but the small ID space is the root cause.

**Proposed mitigation (two changes, both in `internal/server/`):**
1. **Increase channel ID to `uint32`** in `store.go` and `server.go`. This expands the
   space to ~4 billion channels, making distributed exhaustion impractical.
2. **Add per-IP channel allocation limit** (e.g., 10 active allocations per /32 per
   day). Track this in `MemoryStore` alongside the channel map. If the limit is
   exceeded, `AllocateChannel` returns an error. This prevents a single (or small
   group of) IPs from consuming a meaningful fraction of the ID space.

**Effort estimate:** Small. Type change in structs and function signatures, plus a
counter map in the store.

#### SUM-03: #3 — CPace hash-to-curve uses `math/big` (not constant-time) — [OPEN]

**Source:** deepseek-v4 #3

**Description:** The SSWU hash-to-curve implementation (RFC 9380) in
`internal/crypto/hash_to_curve.go` uses Go's `math/big` package for all field
arithmetic. While the algorithm structure has no branches on secret data, `math/big`
internally allocates memory based on value size and uses variable-time algorithms
for modular exponentiation (`inv()`, `sqrtRatioP256`). The password goes through
SHA-256 before SSWU, so direct extraction is not straightforward, but a
close-proximity attacker with fine-grained timing measurements could theoretically
learn information about the CPace password.

**Current state:** Unfixed. No known practical exploit — the timing signal is noisy
over a network, and the password is already hashed before the variable-time math
runs.

**Proposed mitigation (two options, in `internal/crypto/hash_to_curve.go`):**
- **Option A:** Replace `math/big` field arithmetic with a constant-time library.
  Use `filippo.io/nistec` (already an indirect dependency) or `cloudflare/circl`
  for constant-time P-256 field operations. This eliminates the variable-time
  allocations and modular exponentiation.
- **Option B:** Accept as documented limitation. Add a comment in `hash_to_curve.go`
  noting the theoretical risk and explaining why exploitation is impractical: the
  password is SHA-256-hashed before the variable-time math, and CPace uses the
  result only as a generator point (not a private key).

**Effort estimate:** Option A is large (rewrite field arithmetic in
`hash_to_curve.go`). Option B is small (documentation only).

#### SUM-04: L-01 / #7 — Rate limiter bucket map has no hard cap — [OPEN]

**Source:** flash-max L-01, deepseek-v4 #7

**Description:** The `RateLimiter.buckets` map in `internal/server/ratelimit.go` grows
for every distinct HMAC-hashed IP prefix seen. Cleanup runs every 10 minutes,
removing buckets inactive for 30 minutes. Between cycles, a botnet with many IPs
can create arbitrarily many entries (~88 bytes each). An attacker with large IPv6
/64 subnets could cause memory pressure.

**Current state:** Unfixed. Daily salt rotation clears all buckets, bounding the
window to at most one day.

**Proposed mitigation (in `internal/server/ratelimit.go`):**
- Add a hard cap on the number of buckets (e.g., 100,000 entries).
- When the cap is exceeded, evict the least-recently-seen bucket before inserting a
  new one. This can be implemented with an LRU-linked list or by tracking the oldest
  access time and scanning on insert (the map is small enough that scanning is fast).
- Log a warning when the cap is approached (e.g., >80% full) for observability.

**Effort estimate:** Small. Add a `maxBuckets` field and eviction logic in `Allow()`.

#### SUM-05: #8 — Error message text reveals internal failure counter state — [OPEN]

**Source:** deepseek-v4 #8

**Description:** In `internal/server/server.go` (relay loop), the server sends
different error messages depending on whether the CPace failure threshold has been
reached:
- `"unexpected message type: channel terminated"` (when threshold reached)
- `"unexpected message type"` (when threshold not reached)

A client can infer the internal failure counter state from which message it
receives. This leaks whether other CPace failures have occurred on the same
channel.

**Current state:** Unfixed.

**Proposed mitigation (in `internal/server/server.go`):**
- Use the same generic error message text regardless of internal state:
  `"unexpected message type"` in both cases.
- The `dropChannel` call itself is the real action — the client already knows the
  connection is being closed. The exact reason text adds no value to the client.

**Effort estimate:** Trivial. Change one string literal.

#### SUM-06: L-02 / #9 — UDP mux channels silently drop packets when full — [OPEN]

**Source:** flash-max L-02, deepseek-v4 #9

**Description:** In `internal/network/network.go`, the UDP mux uses non-blocking
channel sends with a `default:` branch that silently drops packets:

```go
select {
case m.probeCh <- udpDatagram{data: pkt, addr: addr}:
default:  // drop
}
```

`quicCh` has buffer 256, `probeCh` has buffer 64. When either buffer is full
(under heavy load or DoS), packets are dropped without any signal. QUIC
retransmission handles lost QUIC packets, and the hole-punch retry mechanism
handles lost probes, so functionality is preserved — but performance degrades.

**Current state:** Unfixed. The drop-on-overflow is intentional for backpressure
handling, but the silent nature makes debugging hard.

**Proposed mitigation (in `internal/network/network.go`):**
- Log drops at debug level when a packet is dropped: `logDebug("dropped UDP
  packet: %s channel full (len=%d)", channelName, len(ch))`.
- Consider increasing buffer sizes: 256 → 512 for `quicCh`, 64 → 128 for
  `probeCh`. This reduces drop probability under normal load without
  significantly increasing memory.
- For probe packets specifically, the 200ms retransmit in `HolePunch` already
  handles drops — the larger buffer just reduces latency variance.

**Effort estimate:** Small. One log line and two constant changes.

#### SUM-07: L-05 — `SafeDestinationPath` may overwrite after 9,999 collisions — [OPEN]

**Source:** flash-max L-05

**Description:** In `pkg/transfer/transfer.go`, `SafeDestinationPath` appends
numeric suffixes `filename(1)`, `filename(2)`, ... up to `filename(9999)` to avoid
overwriting existing files. If all 9,999 candidates already exist, the loop exits
and returns the last candidate (`filename(9999)`) **without** checking whether it
exists. The file would be overwritten.

**Current state:** Unfixed. Requires 9,999 pre-existing files with the same base
name — pathological in practice.

**Proposed mitigation (in `pkg/transfer/transfer.go`):**
- After the loop, check if the 9,999th candidate exists. If it does, return an
  error: `"too many file collisions for %s"` instead of silently overwriting.
- Alternatively, extend the search beyond 9,999 (e.g., up to 999,999) but with
  an existence check on the final fallback.

**Effort estimate:** Trivial. Add one `os.Stat` call after the loop.

#### SUM-08: L-03 — SAS word selection has non-uniform bias — [CLOSED]

**Source:** flash-max L-03

**Description:** In `internal/crypto/crypto.go`, SAS word selection uses a double
modulo (`% 256` then `% len(list)`), which biases earlier entries in the word
lists if `len(list)` does not evenly divide 256.

```go
idx := int(keyMaterial[i]) % 256
if i%2 == 0 {
    words[i] = pgpWordListEven[idx%len(pgpWordListEven)]
} else {
    words[i] = pgpWordListOdd[idx%len(pgpWordListOdd)]
}
```

**Closed in:** v0.15.0 — replaced PGP word lists (256 entries each) with EFF
Short Wordlist 1 (1296 entries) and rejection sampling on uint16 values. No
double-modulo bias. The fallback path (`byte % 1296`) has theoretical modulo
bias but is unreachable with 32-byte key material. See
`internal/crypto/crypto.go:SASFromBytes`.

#### SUM-09: L-04 — `dropChannel` has small race window between read and delete — [OPEN]

**Source:** flash-max L-04

**Description:** In `internal/server/server.go`, `dropChannel` releases the mutex
before calling `DeleteChannel`:

```go
s.mu.Lock()
conns := s.waiters[channelID]
delete(s.waiters, channelID)
s.mu.Unlock()
// ... send errors, then:
_ = s.store.DeleteChannel(channelID)
```

Between releasing the mutex and calling `DeleteChannel`, a new channel with the
same ID could be allocated via `AllocateChannel`. `DeleteChannel` would then
delete the newly allocated channel.

**Current state:** Partially fixed. v0.16.1 (H4) moved `WriteJSON` inside the lock
to prevent concurrent write races, but `DeleteChannel` remains outside the lock.
The race window between `delete(s.waiters)` and `DeleteChannel` still exists — a
new allocation could hit the same ID in the microsecond window.

**Proposed mitigation (in `internal/server/server.go`):**
- Move `DeleteChannel` inside the lock, before releasing it. This eliminates
  the window entirely:
  ```go
  s.mu.Lock()
  conns := s.waiters[channelID]
  delete(s.waiters, channelID)
  _ = s.store.DeleteChannel(channelID)
  s.mu.Unlock()
  ```
- Note: `DeleteChannel` acquires its own lock in `MemoryStore`. This is safe as
  long as the lock order is consistent (server mutex → store mutex). Currently
  `AllocateChannel` also acquires server mutex then store mutex, so the order is
  consistent.

**Effort estimate:** Trivial. Move one line.

#### SUM-11: #2 — Signaling client always sets `InsecureSkipVerify: true`

**Source:** deepseek-v4 #2

**Description:** In `internal/network/signaling.go`, the TLS config always sets
`InsecureSkipVerify: true`. When `pinnedFingerprint` is set, a custom
`VerifyPeerCertificate` callback provides cert-pinning security. When
`pinnedFingerprint` is empty (e.g., `trust` command), there is no certificate
validation at all — only encryption.

**Current state:** Won't fix. The signaling server uses a self-signed certificate,
so CA chain verification would always reject it. The TOFU bootstrap phase
(`trust` without `--fingerprint`) is intentionally unauthenticated — the
connection is encrypted but identity is not verified. Operational guidance
already documents that `trust` must run over a trusted network.

**When `--fingerprint` is set:** The `VerifyPeerCertificate` callback (added per
deepseek-v4 #1, fixed in commit 3d16227) checks the fingerprint during the TLS
handshake, providing strong identity verification via cert pinning.

#### SUM-12: #11 — Metadata filename protected by `filepath.Base` on both sides

**Source:** deepseek-v4 #11

**Description:** The receiver strips directory components from the sender-provided
filename using `filepath.Base` (`internal/cli/rx.go`), and then
`SafeDestinationPath` in `pkg/transfer/transfer.go` applies `filepath.Base`
again. Both layers use the same Go standard library function.

**Current state:** Won't fix. Correct as-is — the double protection means a bug
in one layer would still be caught by the other. No known bypass exists for
Go's `filepath.Base` semantics in this context.

#### SUM-02: H-04 / #10 — Server private key stored in YAML config file

**Source:** flash-max H-04, deepseek-v4 #10

**Description:** The server's ECDSA P-256 private key is stored as PEM inside
`~/.config/hermod/config.yaml` (file permission `0o600`). Any process running as the
same user, or any backup/indexing tool that reads config files, can extract the
private key. The YAML is not encrypted at rest.

**Current state:** Won't fix. The design choice (single config file avoids a separate
keystore) is documented in CONTEXT.md (Security Model). The key is ephemeral —
regenerated on `hermod serve` if missing — so the window of compromise is bounded
by the server's uptime. For the intended usage (ephemeral P2P file transfers in
trusted environments), the server key is short-lived and never leaves the machine.

**Background:** This was flagged as H-04 in the flash-max audit but is a deliberate
trade-off: a single config file is simpler than a separate keystore with its own
permissions. The file is created with `0o600` (owner read/write only). Operational
guidance for stronger isolation (containers, systemd `LoadCredential`, bind mounts)
is documented in CONTEXT.md.
