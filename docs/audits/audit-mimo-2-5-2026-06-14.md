# Security & Code Audit Report

**Date:** 2026-06-14
**Scope:** Full repository (hermod v1.0.3)
**Auditor:** Vibe Agent (automated analysis)

## Summary

Hermod is a well-designed, security-conscious P2P file transfer tool. The cryptographic protocol is strong: hybrid post-quantum KEM (ML-KEM-768 + X25519), CPace PAKE, TLS 1.3 with X25519MLKEM768, and AES-256-GCM endpoint bundle encryption. The server is designed as an untrusted relay — no payload ever passes through it.

This audit found **no critical vulnerabilities**. Two findings rated MEDIUM and several LOW items are detailed below.

---

## Findings

### S-01: `InsecureSkipVerify: true` in production TLS configs — MEDIUM

**Files:**
- `internal/network/signaling.go:57`
- `internal/network/network.go:303`
- `internal/network/network.go:325`

All three locations set `InsecureSkipVerify: true` and then install a custom `VerifyPeerCertificate` callback for SPKI pinning. This is a common Go pattern but carries risk: if the callback is ever removed or bypassed (e.g. during refactoring), TLS verification silently disappears.

**Mitigation already present:** Each callback uses `crypto/subtle.ConstantTimeCompare` for fingerprint comparison. The `InsecureSkipVerify` is documented as intentional.

**Recommendation:** Add a code comment on each `InsecureSkipVerify = true` line linking to the callback and stating "DO NOT REMOVE" — a lightweight guardrail. Consider a lint rule or test that asserts the callback is always set when `InsecureSkipVerify` is true.

---

### S-02: Trust-on-First-Use (TOFU) bootstrap — MEDIUM (design)

**File:** `internal/network/signaling.go:56-73`, `internal/cli/trust.go`

The `hermod trust` command connects to a server without certificate verification (TOFU). An active MITM attacker on the network during the initial `trust` call can pin a fraudulent certificate. Subsequent `tx`/`rx` commands would trust the attacker's server.

**Mitigation already present:** README and `--help` text warn the user to run `trust` over a trusted network. The `--fingerprint` flag allows pre-known fingerprint verification, bypassing TOFU entirely.

**Recommendation:** No code change needed — the design is sound for the use case. Consider adding a TOFU-specific warning banner in `trust` output when no `--fingerprint` is provided.

---

### S-03: Trust URL scheme check operator precedence — LOW

**File:** `internal/cli/trust.go:53`

```go
if len(serverURL) < 4 || serverURL[:4] != "wss:" && serverURL[:3] != "ws:" {
```

Go operator precedence makes this evaluate as `(len < 4) || (([:4] != "wss:") && ([:3] != "ws:"))`, which is correct. However, the expression is fragile — adding parentheses would make intent explicit and prevent future editing errors.

**Recommendation:** Add explicit parentheses:
```go
if len(serverURL) < 4 || (serverURL[:4] != "wss:" && serverURL[:3] != "ws:") {
```

---

### S-04: WebSocket `CheckOrigin` rejects browser connections only by Origin header — LOW

**File:** `internal/server/server.go:107-109`

```go
CheckOrigin: func(r *http.Request) bool {
    return r.Header.Get("Origin") == ""
},
```

This blocks browser-sourced requests (which always send Origin) while allowing CLI clients (which do not). Non-browser HTTP clients can also omit Origin, so this is not a strong auth boundary — but it is not intended to be. The signaling protocol itself is authenticated via CPace PAKE.

**Recommendation:** No change needed. The check is a defense-in-depth layer, not a primary control.

---

### S-05: Config fallback to `/tmp` when `$HOME` unavailable — LOW

**File:** `internal/config/config.go:64`

```go
return fmt.Sprintf("/tmp/hermod-%d", os.Getuid())
```

If `$HOME` cannot be resolved, the config (including the server private key) is written to `/tmp/hermod-<uid>`. On shared systems, `/tmp` may be world-readable despite 0o600 file permissions (e.g. if the system mounts `/tmp` with `nosuid,nodev` but not `noexec`). This is a narrow edge case documented as a fallback.

**Recommendation:** Consider logging a warning when falling back to `/tmp` so the operator is aware.

### S-06: No hardcoded secrets — PASS

All secrets (TLS private keys, HMAC salts, cryptographic nonces) are generated at runtime via `crypto/rand`. No hardcoded keys, passwords, or tokens found in source code or configuration files.

---

### S-07: Input validation — PASS

- Transfer codes are parsed with bounds checking (`ParseTransferCode` validates format and word count).
- Handshake blobs are parsed with fixed-length checks (`ParseSenderHandshakeBlob`, `ParseReceiverHandshakeBlob`, `ParseSenderBundleBlob`).
- WebSocket messages are limited to 64 KiB (`maxMessageSize`).
- Length-prefixed metadata is capped at 1 MiB (`readLenPrefixedMax`).
- Endpoint bundles are JSON-decoded without arbitrary size growth (limited by WebSocket message size).
- File path traversal is defended via `filepath.Base` in both `rx.go:567` and `transfer.go:85`.

---

### S-08: Error handling — PASS

Every error return is handled. No empty `catch` blocks. Server error messages to clients are generic ("operation failed") to prevent information leakage about channel existence.

---

### S-09: Resource cleanup — PASS

`defer` is used consistently for:
- WebSocket connections (`server.go:248`, `signaling.go:150`)
- TLS listeners (`server.go:130`)
- UDP connections (`network.go:206`)
- QUIC connections (`tx.go:414`, `rx.go:362`)
- Context cancellation (`tx.go:93`, `rx.go:55`)
- File handles (`tx.go:566`, `rx.go:407`)

The `mux.Close()` and `sigRaw.Close()` calls use `defer` to guarantee cleanup.

---

### S-10: Concurrency safety — PASS

- `MemoryStore` uses `sync.Mutex` for all map operations.
- `RateLimiter` uses `sync.Mutex` for bucket access and salt rotation.
- `Server.waiters` is protected by `sync.Mutex`; the lock is held during connection writes to prevent Gorilla WebSocket concurrent-write panics (`server.go:559`).
- `packetMux` channels have appropriate buffer sizes (256 for QUIC, 64 for probes).
- `SignalingClient.done` channel is closed exactly once via `sync.Once` (`signaling.go:149`).

---

### S-11: Race conditions — PASS (static analysis)

The `go test -race ./...` suite passes for all packages except a known-flaky e2e test (`TestCLITransferText`) which times out at 60s — a test infrastructure issue, not a data race.

### S-12: Cryptographic implementation quality — PASS

| Primitive | Implementation | Assessment |
|---|---|---|
| CPace PAKE | P-256, SSWU hash-to-curve (RFC 9380) | No timing side channel (no data-dependent branches on secrets) |
| Scalar generation | Rejection sampling on `crypto/rand` | Unbiased, no modulo bias |
| AES-256-GCM | `crypto/aes` + `cipher.NewGCM` | Random 12-byte nonce from `crypto/rand` |
| ML-KEM-768 | Go 1.25 stdlib `crypto/mlkem` | FIPS 203 compliant |
| X25519 ECDH | Go 1.25 stdlib `crypto/ecdh` | Constant-time |
| TLS 1.3 | Go stdlib, X25519MLKEM768 only | No classical fallback (as designed) |
| SPKI fingerprint | SHA-256 of PKIX public key | Constant-time comparison via `subtle` |
| Hole-punch nonce | SHA-256(hybridKey \|\| "hermod-holepunch-v1") | 64 bits of entropy per probe/ack packet |

---

### S-13: Rate limiting — PASS

- Token bucket per IP prefix (IPv4 /32, IPv6 /64).
- Bucket keys are HMAC-SHA256(daily-rotating salt, prefix) — raw IPs never stored.
- Stale buckets cleaned up every 10 minutes (30-minute max age).
- Separate rate limiters for `/cert`, WebSocket upgrade, and channel join.
- UDP reflection endpoint rate-limited independently.
- Per-IP channel cap (default 100) prevents resource exhaustion.

---

### S-14: Denial-of-service protections — PASS

- Channel TTL with GC every 60 seconds.
- Max blobs per channel (default 10).
- Max CPace failures (default 3) before channel termination.
- Per-IP channel cap (default 100).
- WebSocket idle timeout (default 600s).
- HTTP server timeouts: ReadHeaderTimeout 10s, ReadTimeout 30s, WriteTimeout 30s, IdleTimeout 120s.
- UDP reflection uses 2-second read timeout.

## Code Quality Observations

### Q-01: Large files approaching module boundaries

- `internal/cli/tx.go`: 872 lines
- `internal/crypto/crypto.go`: 746 lines

Both are cohesive and single-purpose. `tx.go` contains the complete send flow plus helpers. `crypto.go` contains CPace, AES-GCM, SAS, identicon, and transfer code generation. Consider splitting `crypto.go` into `cpace.go`, `aes.go`, `sas.go` if the file grows further.

### Q-02: E2E test flakiness

`TestCLITransferText` fails with a 60-second timeout in CI. The test starts a real signaling server and runs `tx`/`rx` as subprocesses. The timeout suggests a race in process startup or WebSocket connection establishment. Not a security issue but affects CI reliability.

### Q-03: `lint_test.go` uses `exec.Command` with user-controlled tool version

`lint_test.go:55` runs `go run golang.org/x/tools/cmd/deadcode@latest`. The `@latest` version tag means the exact binary changes over time. This is acceptable for a lint tool but would be flagged by dependency pinning rules for production code.

## Conclusion

The codebase demonstrates strong security engineering. The cryptographic design is sound, with post-quantum hybrid KEM, constant-time implementations, and proper nonce handling. The server is correctly designed as an untrusted relay. Rate limiting, input validation, and resource cleanup are thorough.

The two MEDIUM findings are design-level observations (TOFU and `InsecureSkipVerify` pattern) that are well-mitigated by documentation and existing controls. No critical or high-severity issues were found.
